# 3D Model Sourcing & Authoring Specification

- **Date:** 2026-08-29
- **Purpose:** Define what the 3D atlas must satisfy to be usable by Anatomy Pro,
  so a model can be bought, commissioned, or adapted without discovering blockers late.

Hand this document to a vendor or a 3D artist. Everything in §2 is a hard requirement;
a model failing any of it cannot drive the app without rework.

---

## 1. Why this matters more than it looks

The app's core interaction is *tap a structure, get its name*. That requires the model
to be **segmented into separately addressable, stably named nodes**. A visually
beautiful anatomy model welded into a handful of meshes is worthless here — no amount
of application code recovers per-structure identity from merged geometry.

The second-order trap: a model can be segmented but **unstably** named (auto-generated
names, or names that change between vendor releases). Then every model update silently
breaks the structure database and the quiz answer keys. Stable identifiers are as
important as the geometry.

---

## 2. Hard requirements

### 2.1 Segmentation

- Every anatomical structure the app can name is its **own node** in the scene graph.
- Bilateral structures are **separate nodes** with explicit laterality, not mirrored
  instances sharing one name.
- No structure spans multiple nodes *unintentionally*. Where it must (vertebral column,
  muscle groups), the grouping is expressed through the node hierarchy, not by
  coincidence of naming.

### 2.2 Naming

- Node names are **stable across releases**. A structure's identifier must never be
  reused for a different structure.
- Naming carries, at minimum: the structure's Latin (Terminologia Anatomica) name and
  its laterality.
- Recommended node-name format, ASCII only, no spaces:

  ```
  <ta_code>__<latin_slug>__<L|R|M>

  A02_4_01_001__scapula__L
  A02_4_01_001__scapula__R
  A02_2_00_000__columna_vertebralis__M
  ```

- Where a TA code is unknown, a stable vendor identifier is acceptable **provided it is
  documented and guaranteed stable**.

### 2.3 Hierarchy

- Nodes are parented to reflect anatomical containment (system → region → structure →
  sub-structure).
- The hierarchy is used directly for quiz distractor difficulty, so it must be
  anatomically meaningful rather than an artifact of modelling convenience.

### 2.4 Geometry

- Manifold, no zero-area faces, no duplicate vertices, consistent outward normals.
- No self-intersections *between* structures beyond what anatomy genuinely requires.
- Correct relative scale across the whole body; a structure must not be modelled to a
  different scale than its neighbours.

### 2.5 Format, units, orientation

- Deliverable as **glTF 2.0** (`.glb`) or a Blender `.blend` that exports cleanly to it.
- Units: metres. A full adult body approximately 1.7 m tall.
- Orientation: Y-up, model facing −Z, origin at the floor between the feet.
- Materials: PBR metallic-roughness. Textures are **not required** — the app shades
  structures procedurally and recolours them for highlighting.

### 2.6 Licensing

The licence must permit: commercial use, redistribution as part of a compiled mobile
application, and modification (decimation, re-chunking, format conversion).

Watch specifically for clauses forbidding **redistribution as an asset**. On-device
content packs are arguably exactly that, and several 3D marketplace licences prohibit
it. Get this in writing before purchase.

## 3. Performance targets

These are **targets to validate in Phase 0**, not guarantees. They exist so a vendor
knows the shape of the constraint.

| Metric | Target |
|---|---|
| Triangles per structure, after decimation | 2,000–5,000 average |
| Simultaneously visible structures | 300–800 |
| Resident triangles per loaded region | ≤ 3 M |
| Draw calls per frame | ≤ 800 |
| Resident memory per loaded region | ≤ 400 MB |
| Frame rate | 60 fps sustained, mid-range Android and older iPhone |

**Source models may be far denser than this and that is acceptable** — decimation is a
pipeline step. What matters is that the source is *clean enough to decimate well*.
Dense but well-formed beats light but broken.

LODs are generated by the pipeline, not supplied by the vendor.

## 4. Candidate sources

| Source | Coverage | Naming | Licence | Cost |
|---|---|---|---|---|
| **Z-Anatomy** | Full body, 7,000+ structures | Latin, TA-based, organised and labelled | CC BY-SA 4.0 | Free |
| **BodyParts3D** | Full body, ~3,000 parts | Anatomical, less curated | CC BY-SA 2.1 (JP) | Free |
| **Commercial medical vendor** | Varies — verify per-structure segmentation | Usually good | Negotiated; check asset-redistribution clause | Thousands to five figures |
| **Commissioned** | Exactly what you specify | Exactly what you specify | You own it | Highest; longest lead time |

### 4.1 Z-Anatomy — recommended for Phase 0 regardless of the final choice

Built on BodyParts3D by medical illustrator Gauthier Kervyn, distributed as Blender
files. Structures have been re-meshed, renamed, organised, and labelled, and it carries
3,500+ definitions that can seed the structure database directly.

It costs nothing and answers the feasibility question within days. Even if the shipping
product ends up on a commercial atlas, **Phase 0 should run on Z-Anatomy** — there is no
reason to spend money before knowing the interaction works.

### 4.2 The share-alike question, stated plainly

CC BY-SA obliges attribution and requires derivatives of **the licensed work** to carry
the same licence. Applied here:

- Your converted, decimated, re-chunked glTF packs are derivatives → they must be
  published under CC BY-SA, with attribution.
- Your Kotlin application, quiz engine, structure database schema, backend, and UI are
  **separate works** → they remain yours.

Practically: a competitor could take your meshes. They could not take your app. Whether
that is acceptable is a business judgement, not a legal blocker.

**If it is unacceptable**, there are two clean exits:
1. Buy a commercially licensed atlas with explicit redistribution rights.
2. Keep the open model and move the paywall from *content* to the *learning system* —
   free atlas browsing, paid quizzes, progress, and daily competition. This sidesteps
   share-alike entirely, since the paid surface contains none of the licensed work.

## 5. Acceptance checklist

Run before accepting any model. Automate as a pipeline script so re-runs are cheap.

- [ ] Every intended structure is a discrete node
- [ ] Node names match the agreed convention and are unique
- [ ] Node names are documented as stable across future releases
- [ ] Bilateral structures carry correct, distinguishable laterality
- [ ] Hierarchy is anatomically meaningful, not modelling-convenient
- [ ] Units are metres; full body is approximately 1.7 m
- [ ] Orientation and origin match §2.5
- [ ] No zero-area faces, no duplicate vertices, normals consistent
- [ ] Exports to `.glb` without geometry loss
- [ ] Decimates to the §3 budget without visible structural degradation
- [ ] Licence permits commercial use, modification, and in-app redistribution
- [ ] A named list of every structure is supplied, machine-readable

The final item is easy to forget and expensive to reconstruct. Insist on it.

---

## 6. Recommendation

> Decided 2026-10-06: Z-Anatomy, taking exit 2 of §4.2 — the paywall moves to the learning
> system. See the design spec §29.

1. **Run Phase 0 on Z-Anatomy.** Free, immediate, and sufficient to answer the only
   technical question that matters.
2. **Defer the sourcing decision** until Phase 0 has produced real numbers on
   decimation quality and frame rate.
3. **Decide by the end of Phase 1**, when the pack pipeline is proven and the true cost
   of adapting a source is known rather than guessed.

Buying a model before Phase 0 spends money to remove a risk that Phase 0 removes for
free.
