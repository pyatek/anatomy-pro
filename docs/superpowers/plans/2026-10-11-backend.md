# Backend (Phase 3) Implementation Plan

**Spec:** `docs/superpowers/specs/2026-10-11-backend-design.md`. Section numbers below are
that document's unless they say "design" (the 2026-08-29 spec) or "all-screens".

**What this plan is, and is not.** It is the order of work, with each task's files, what it
must expose, the tests that define it, and what "done" means. It is **not** yet a
line-by-line plan with the code written out, as the screen plans were. Each stage should be
expanded into one of those before it is executed, against the code as it then stands — the
screen plans went stale within a day where the code under them moved (state-of-play,
2026-10-10), and this plan spans weeks.

## Global constraints

- Repository root is `~/StudioProjects/AnatomyPro`.
- Shared code is tested on every target it has. `core-quiz` and `api-contract` gain a JVM
  target; a test that passes on one target and not another is a failure.
- Server tests use real PostgreSQL through Testcontainers (design §15). No in-memory database.
- No secret, token, ID token or purchase token is ever logged or committed.
- Every state-changing endpoint is idempotent (§6.2, §8.1); each has a test that calls it twice.
- No `Co-Authored-By` trailers on commits.
- The contracts in `shared/core-data` change only where §4.5 says they do.

on a laptop.

## Stage 1 — Packs from a bucket (ticket C010)

Independent of the server. Unblocks screens 03 and 19 in release builds.

**1.1 The index and the publish step.** `pipeline/anatomypro_pipeline/publish.py`,
`pipeline/tests/test_publish.py`. Builds an index entry from a pack's `manifest.json` and
`.glb` (id, version, labels, byte size, SHA-256, URLs); uploads through an S3-compatible
client; reads back and compares; rewrites `index.json` last; refuses an existing version.
Tests against a local directory standing in for the bucket: a publish, a refused overwrite,
an index never pointing at a missing file when an upload fails half way.

**1.2 The download engine.** `shared/core-network` (new module), `PackDownloader`. Ktor
client, `Range` requests, a temporary file, SHA-256 over the whole file. Pure of Room.
Tests with Ktor's mock engine: a clean download; an interruption then a resume that asks only
for the missing bytes; a server that ignores `Range`; a checksum mismatch that deletes the
partial file.

**1.3 `CdnPackRepository`.** Implements `PackRepository`: the index merged with what is
installed; download, cancel, delete; install is the manifest into the database and the file
moved into place together (§9.2). Tests: every `PackStatus` reached; cancel mid-download
leaves nothing installed; a pack is never visible half-written; delete frees the file and
keeps the structure rows (design §24.3).

**1.4 Eviction.** Least-recently-used packs released under memory pressure (design §14).
Tests under a budget.

**1.5 Contract clean-up and wiring.** Remove `PackState.entitlement` and
`PackFailure.NOT_ENTITLED` (§4.5); `rememberAppDependencies()` supplies `CdnPackRepository`;
onboarding becomes three steps in release builds; the APK stops bundling packs other than
the first. Hand run: screens 03 and 19 against a real bucket on both platforms.

**Done when:** a release build with no bundled pack installs the skeleton from the CDN,
survives airplane mode half way, and resumes.

## Stage 2 — Code both ends share

**2.1 `core-quiz`.** Move `QuizNode`, `QuizGraph` and their tests out of `core-data/quiz`
into `shared/core-quiz`; add `jvm()` to it and to `core-model`. `core-data` depends on it.
The golden test now runs on three targets and must agree on all of them.

**2.2 `api-contract`.** `@Serializable` types for every request and response in §5 to §8 and
one `ApiError(code, message)` with the codes as an enum. A round-trip test per type, and one
that fails if a field is added without a default (old clients must keep parsing new servers).

**Done when:** `./gradlew allTests` is green with the new targets and nothing else has changed.

## Stage 3 — A server that runs

**3.1 The module.** `backend/` : Ktor (Netty), kotlinx.serialization, HikariCP, Flyway, a
plain SQL access layer (no ORM — the queries in §6.3 and §5.3 are the design). `Dockerfile`,
`compose.yaml` with caddy, backend and postgres. `GET /health`.

**3.2 Test harness.** Testcontainers PostgreSQL started once per test run; each test in a
schema of its own; `testApplication` for endpoints.

**3.3 Accounts.** V1 migration: `account`, `device_token` (hash only), `nickname` rules.
`POST /v1/auth/anonymous`, `PUT /v1/account/nickname`, `DELETE /v1/account`, bearer
authentication. Tests: the stored value is a hash; a revoked token is refused; nickname
length, charset, case-insensitive uniqueness, the blocklist; deletion leaves no row.

**3.4 Limits and errors.** One error shape; rate limits per token and per address on the
auth endpoints; request logging that redacts `Authorization`.

**Done when:** `docker compose up` on a laptop serves `/health` over TLS with a local
certificate, and an account can be made, renamed and deleted with `curl`.

## Stage 4 — Content, the daily, the boards

**4.1 Ingest.** Migrations for `structure`, `structure_text`, `structure_verification`;
`backend ingest <manifest>` and `backend verify <file>` (§10). Tests: a re-ingest replaces
names and leaves verifications; a verification whose hash no longer matches is not counted.

**4.2 The day's set.** `daily_set` (date, topic, seed, the questions, stored). Generated on
first request inside a transaction that tolerates two requests arriving together. Tests: the
stored set equals `QuizGraph` for that seed; a content update does not change a stored set;
no eligible topic is reported as unavailable; a topic is not repeated within six days when
there are enough.

**4.3 Attempts.** `daily_attempt` (account, date unique; started, submitted, timed, correct,
elapsed, ranked, the answers). The three endpoints of §6.2. Tests: all of §12's daily
integrity list.

**4.4 Boards.** The two endpoints of §7; the streak maintained on submit. Tests: §12's
ranking list; a streak across a missed day; yesterday's streak still standing today.

**4.5 Gating.** A subscriber check in front of the daily and the boards, behind an
interface that Stage 7 implements; until then a configuration flag grants everyone, **off by
default**, so a build cannot ship with the gate open by accident.

**Done when:** with fixture verifications ingested, two `curl` sessions can play the same
daily and see each other on the board.

## Stage 5 — The app talks to it

**5.1 Token storage.** `expect`/`actual` secure storage: Keychain, and a Keystore-backed
store on Android. Tested on both.

**5.2 The repositories.** `KtorDailyRepository`, `KtorLeaderboardRepository`. Mapping from
the wire to the contract, including filling `correctIndex` (§4.1) and turning no-connection
into `DailyQuiz.Unavailable` (§6.4).

**5.3 Client against server.** A JVM test source set that starts the real server in-process
and drives it through these repositories (§12). The existing ViewModel tests for the daily
and the leaderboard are then run a second time against this pair instead of the fakes.

**5.4 The seam.** `rememberAppDependencies()` supplies them. The Today and Ranking tabs lose
their placeholders in release builds. Hand run on both platforms against a server on the
laptop.

**Done when:** a release build plays the daily against a real server and the fakes are used
only by tests and debug switches.

## Stage 6 — Sign-in

**6.1 Verification.** Google and Apple ID tokens against their JWKS, audiences pinned, keys
cached. Tested with tokens signed by a test key and a stubbed JWKS: a good token, a wrong
audience, an expired one, a wrong issuer.

**6.2 Linking and the merge.** `identity` (provider, subject unique). `POST /v1/auth/link`,
`POST /v1/auth/signout`. The three cases of §5.3 and the merge transaction. Tests: each
case; both accounts having played the same day; the merge rolled back whole when any part
fails.

**6.3 The app.** Platform sign-in (Credential Manager on Android, AuthenticationServices on
iOS) behind a small common interface; a place for it on the profile; the nickname field.
This needs screens the prototype does not have — a short design pass first.

**Done when:** an account made on one device is signed into on a second, and the second
shows the first's daily result and place.

## Stage 7 — Subscriptions

**7.1 The model.** `subscription` keyed by the store's own id; `GET /v1/entitlements`,
`GET /v1/plans`.

**7.2 Google.** `POST /v1/purchases/google`, verification through the Play Developer API,
the notifications webhook. Tested against recorded responses.

**7.3 Apple.** `POST /v1/purchases/apple`, JWS verification against Apple's roots, the
notifications v2 webhook. Tested against recorded payloads.

**7.4 Keeping it true.** The daily re-check of subscriptions near expiry; the gate of 4.5
switched from the flag to this.

**7.5 The app.** Play Billing and StoreKit 2 behind `EntitlementRepository`, which now
reports what the server concluded (§4.5). The paywall's placeholder goes.

**Done when:** a sandbox purchase on each store unlocks the daily on that account, a refund
or expiry locks it again without the app being opened, and a restore on a second device
points the user at sign-in.

## Stage 8 — The box

**8.1** Provision the VPS; Compose with real TLS; the environment file.
**8.2** Nightly encrypted `pg_dump` to a private bucket; the restore drill, timed and written down.
**8.3** The uptime check; log rotation.
**8.4** The deploy: build, push, pull, restart; a rollback that is one command.
**8.5** A dress rehearsal: a fixture daily played across 00:00 UTC by several accounts, with
a deploy in the middle.

**Done when:** the restore drill has been done once for real, and the rehearsal found
nothing that is not written down.
